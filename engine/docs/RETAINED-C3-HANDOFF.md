## Existing bounded structural-to-C3 path

The [accepted prepared owner](PREPARED-STUDY-OWNER.md) and [structural admission plan](STRUCTURAL-ADMISSION-PLAN.md) already supply the lower handoff:

1. A caller owns Runtime and an empty prepared f64 Harness. It supplies a pinned `shared_ptr<const ActiveAssembly>` v2 source, logical session identity, explicit `AdmissionBindings`, reservation domain and separate preparation/operation work allowances. Bindings include conceptual roles/units, physical intrinsics, comparison topology/precision and nonempty focus. Native layout pointers belong to the caller's live Program. They are not coordinates or an inferred hierarchy.
2. `PreparedStudyOwner::prepare` seals the existing `StructuralAdmissionPlan`, retains the immutable source pin and reserves claim/scale metadata. This stage publishes no native model. `ActiveAssembly::bind_structure` is available as a source handoff, but the legacy session does not dispatch to it. The plan builder directly validates the owned projection/membership source instead of requiring a second flattened input producer.
3. `PreparedStudyOwner::bootstrap` authorizes owner and logical handle, verifies current empty native context/generation, then calls private `Harness::stage_current_admission(..., commit=true, bootstrap=true, focus...)`.
4. `Placement::stage` generates native placement; `update_prepared_impl` uses `BootstrapCommit`, calls `LiveHierarchy::prepare_refresh` / `stage_refresh`, commits native claims/source rows and calls `LiveHierarchy::commit_refresh`. It synchronizes, verifies status, commits the source generation and finishes the hierarchy. This existing combined bootstrap transaction establishes initial C3, focus and contacts together.
5. Only after native success does the logical owner resolve each sealed command through `PreparedStorage::resolved`, validate full context/incarnation/address/record/header identity, and publish its actual claim tables. Owner phase `Published` is the map visibility boundary.
6. `owner.tick` delegates to contact-safe `tick_prepared` and follows successful native generation changes. `viewport::observe(PreparedStudyOwner,...)` reads current native physical state using the committed associations. Authorization, logical source generation, native generation and completed tick remain distinct. Detached reports and source projection tables do not become a second numerical authority.

**This bootstrap does not call `Harness::install_live_hierarchy` / `LiveHierarchy::install`.** The standalone C3-1 entry takes already populated source accounting and an explicit `WeightedCascadeSpec`. #370 optimizes that entry's initial packet transport. Combined bootstrap claims fresh bodies/fields and publishes its hierarchy through the existing transaction implementation, which also supports refresh. Adding the standalone installer after bootstrap would duplicate the operation; changing shared refresh transport remains a separately reviewed task. No #370 transfer saving is attributed to the retained bootstrap route here.

## Focused native witness

New `retained_c3_handoff_test` registers four Linux GNU/Clang CTests, 1/2 workers × bulk/direct, under the existing optional viewport build. Its linker-only counters forward real calls to `LiveHierarchy::install` and `commit_refresh`; production libraries have no instrumentation. A real stale-generation standalone-install call must increment the first counter without publishing anything, ruling out a silently inactive trace.

Each mode exercises the retained construction/session boundary above, then the existing aggregate and parts `prepared_owner_fixture` subsets separately. These two small prepared studies are **not** the full 16-body retained study. Each proves:

- Source pin survives release of the preparing caller's `shared_ptr`.
- Zero placement work refuses before either hierarchy publication entry while native execution stays healthy; bootstrap with the configured work allowances then succeeds through one combined commit and zero standalone installs.
- Preparation leaves the logical owner unready. After bootstrap, completed C3 body handles match the published owner claims. Aggregate/parts expose two/three comparisons respectively and native diagnostics return `ok`.
- Foreign owner and stale logical handle are refused. A native prepared tick completes; old association views become stale, a fresh completed observation carries current native generation/tick, and an earlier detached report remains unchanged.
- The logical owner releases its source on teardown while the borrowed Harness/native hierarchy remains alive. Native bootstrap/tick boundaries retain the existing zero C++ new/new[] metadata assertion. This is not full malloc, retained-size or physical-memory accounting.

The test is a behaviour-preserving inspection: no production API, ownership class, physical formula, layout policy, source-count inference or second numerical solve is added.

## Smallest next change and review boundary

The map correction and named witness are the smallest behaviour-preserving change supported by this inspection. A later runtime proposal should add **one explicit prepared-study operation at the active ownership/control boundary**, using the existing plan/owner/bootstrap. It must establish who owns Runtime/layout/Harness/owner, who supplies the pinned v2 recipe and supported comparison/geometry/focus/resource choices, and who receives the existing authorized handle/observation. Legacy v1 submit/refresh/report behavior should remain compatible.

`ActiveSession` currently keeps Runtime private while `AdmissionBindings::layout` requires live Program-owned layout pointers; passing a detached snapshot or simply swapping `bind` for `bind_structure` is not a complete operation. A design must provision that native context within the execution owner and delegate to existing admission/map publication, not expose stale pointers or duplicate the producer. Teardown must release the logical owner before Harness before Runtime. Unsupported v2/local/forest cases must remain explicit refusals until their contracts exist. No automatic comparison policy or Analyst decision-making is supplied by this inspection.

Review the boundary and caller inputs before implementing that operation. Refresh transport, reservation redesign, full accounting, native object-model migration and #324 mathematics remain separate.
